# Отчёты по маркетплейсам — v1.0 (TrueStats + облако)

Ежедневная система отчётов WB+Ozon: заказы по 7 брендам, сводный отчёт
«Общая», аналитика цен. Запускается сама в **07:30 МСК** (cron-job.org →
workflow_dispatch) на облачных раннерах GitHub; подстраховочный сбор без
отправки — 06:45 МСК (schedule). Полное описание версии и все расположения —
`ОБЗОР_ВЕРСИИ_v1.0_2026-07-21.md` в локальной папке проекта 21.

## Конвейер (scripts/run_all_ts.py)

По каждому бренду: сбор → Excel → Google-таблица → Telegram.

- Бренды с `<PREFIX>_TS_TOKEN` — ядро из **TrueStats** (`collect_ts.py`,
  секунды), воронка WB каскадом: async CSV-отчёт → батчи → без воронки;
  история — `history_ts.py`.
- Остальные (ORZAX, LOVE&DOVE) — старый путь `collect.py`/`history.py`.
- После брендов: свод «Общая» (`svod_report.py`: колонки прошлых дней в
  основных листах + полная история по брендам в листах «История
  Общее/ВБ/Озон» (позиция × бренд × день, до 60 дн, сырьё в
  `state/svod_history.json`), утренняя сводка в TG картинкой с разбивкой
  по брендам — `svod_telegram.py`) и цены WB+Ozon из MPStats
  (`prices_update.py`).
- Изоляция брендов, финальный ретрай, анти-дубль (`state/sent_*`), алерт
  о сбоях в служебный TG.

## Монитор цен «мы стали дороже» (scripts/price_watch.py)

Отдельный конвейер (`.github/workflows/price-watch.yml`, раз в 3 часа: 09, 12,
15, 18, 21 МСК), к ежедневному отчёту не привязан. Живая цена берётся **не из MPStats**
(там только дневной срез), а из публичного `card.wb.ru/cards/v4/detail`:
`sizes[0].price.product/100` = цена карточки, цена с WB-Кошельком =
`floor(цена × 0.98)` (сверено с MPStats, расхождений нет). До 100 артикулов на
запрос, без авторизации — таблица на 321 артикул закрывается 4 запросами.

Товарная группа = значение колонки A (тянется вниз, пустая строка —
разделитель). Внутри группы наши бренды сравниваются с минимумом конкурентов и
с «дороже всех», а конкуренты из настройки «Колонки конкурентов» показываются
**поимённо** отдельными колонками — с ценой и артикулом в одной ячейке, чтобы
менеджер копировал артикул прямо из листа. Медианы убраны 30.07.2026: менеджер
ориентируется на самого дешёвого, а медиана рисует рынок дороже, чем он есть.
Конкуренты делятся на группу **А** (якоря, по ним работает правило «стоять на
15–20 % ниже») и **Б** (второй эшелон — остаётся в таблице, но помечен).
Прогоняются все таблицы из `PRICES_GSHEET_ID`.

Сигнал идёт **в обе стороны** от порога (по умолчанию 5 %): мы дороже минимума
конкурентов — теряем продажи; мы дешевле того же минимума — отдаём маржу, цену
можно поднять и всё равно остаться самыми дешёвыми. В сообщении это два
отдельных блока, в листе — красная и зелёная шкалы.

Настройки и состояние — лист **«Мониторинг цен»** в самой таблице цен (порог %,
получатели TG, окно часов, вкл/выкл, список наших брендов, разбивка по брендам).
Состояние там же, поэтому прогоны ничего не коммитят в репозиторий. Раскладка
листа считается от числа настроек (`SUMMARY_ROW`/`HEAD_ROW` из `len(DEFAULTS)`),
и лист со старой раскладкой мигрирует сам — значения настроек при этом
сохраняются, потому что блок переписывается прочитанными, а не дефолтными.

**Разбивка по брендам.** При `Разбивать по брендам = да` сигналы раскладываются
по адресатам: каждый чат получает своё сообщение только со своими брендами и
своими счётчиками. Адрес ищется в настройке «Чаты по брендам»
(`NATURI=-100…:5, SUNSHINE=-100…:7`), затем в `api_keys` по ключу
`<PREFIX>_TG_CHATS` — тем же, что у утреннего отчёта (`Health Form` →
`HEALTHFORM_TG_CHATS`), и только потом падает на «Получатели TG». По умолчанию
`нет` — всё в один адрес.

Лист пересобирается каждый прогон как приоритетный дашборд: над заголовками
строка «Сейчас» (сколько дороже, сколько дороже всех в группе, сколько сильно
дешевле рынка, сколько без цены), дальше строки **отсортированы по остроте**.
Сверху красная зона — где мы дороже всего (от `#E06666` при ≥15 % до бледного
`#FCE8E6` у порога), под ней зелёная — где мы сильнее всего дешевле всех (от
`#93C47D` при ≥20 % до `#D9EAD3`), затем «ок» белым и серым внизу строки без
сравнения. Порядок именно такой: потеря продаж срочнее недобранной маржи.
Цвета считаются в скрипте и кладутся статикой: условных форматов тут
расплодились бы сотни (та же причина, что в `svod_report.py`).

Гистерезис привязан к порогу (выход при сжатии разрыва до половины порога), а
не к нулю: иначе при пороге 5 % позиция висела бы в сигнале, пока не сравняется
с конкурентом вплотную. Побочный эффект — правка порога в листе не ломает
логику выхода, но и не пересматривает уже отправленные сигналы: после смены
порога состояние (колонку «% при уведомлении») имеет смысл очистить, чтобы
получить свежую базу, иначе прилетит пачка ложных «вернулись к рынку».

Анти-спам: сигнал шлётся один раз при появлении, повторно — только если
отставание выросло на ≥3 п.п.; «вернулись в рынок» — когда мы уже не дороже
минимума (гистерезис: цены WB дёргаются на доли процента, иначе позиция на
пороге мигала бы каждый час). Если отправка в TG упала, позиция не
помечается отправленной и сигнал повторится в следующий час.

Лист Ozon в мониторинг не идёт: в нём одни наши SKU, конкурентов нет.

## Управление

Таблица «Пункт управления» (ключ `CONTROL_GSHEET_ID`, папка «034» на Диске):
лист «Настройки» перекрывает api_keys на каждом прогоне (чаты, таблицы,
состав брендов, `CRON_TIME` — сам правит cron-job.org), лист «Дашборд» —
статусы шагов последнего прогона.

## Секреты (Settings → Secrets → Actions)

- `API_KEYS_FILE`, `API_KEYS_EXTRA` — реестры ключей (extra дописывается
  в конец, «последняя строка побеждает» — так ротируются токены);
- `GOOGLE_SA_JSON` — сервисный аккаунт dds-bot (расшарен на все таблицы).

## Ручной запуск / отладка

Actions → «Ежедневный отчёт…» → Run workflow: `brands` (пусто = все),
`skip_tg=1` (собрать без отправки). Excel-файлы — в Artifacts прогона.
История заказов коммитится ботом в `state/` — перед своим пушем делай
`git pull --rebase`.
